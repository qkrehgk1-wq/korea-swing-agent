이 저장소에서 "전체점검-수정-재점검-보완" 사이클을 실행한다. 순서대로, 생략 없이:

## 1. 저장소 상태 확인
- `git status --short --branch`로 워킹트리 상태 확인
- `git fetch origin` 후 `git status --short --branch`로 원격과의 divergence 확인
- 커밋 안 된 변경분이 있으면, 그게 이번 세션에서 만든 것인지 다른 세션이 작업 중인 것인지 구분한다.
  다른 세션 것으로 보이면(내가 방금 만들지 않은 파일), 절대 덮어쓰거나 stash 없이 rebase하지 말 것 —
  `git stash push -u`로 보존 → rebase/push → `git stash pop`으로 복원하는 순서를 따른다.

## 2. 기계적 검증 (병렬로 실행 가능)
- `npx tsc --noEmit` — 타입 오류 0건이어야 함
- `npx vitest run` — 전체 스위트 통과해야 함 (실패 건수·파일명 기록)
- `npx pnpm build` — 프로덕션 빌드 성공 확인 (청크 크기 경고는 무시 가능)
- 모지바케(한글 인코딩 깨짐) 스캔: 최근 변경된 파일 대상으로
  `git grep -lP '\xEF\xBF\xBD'` — 결과 있으면 인코딩 손상 의심

## 3. 코드 리뷰 (사람이 볼 것)
- 이번 사이클에서 변경된 파일들을 실제로 읽고 논리적 결함을 찾는다 — 기계적 검증은 "돌아간다"만 보장하지
  "옳다"는 보장하지 않는다.
- 특히 다음 두 가지를 우선 확인한다 (PROJECT_CHARTER.md에 기록된 이 저장소의 반복 재발 버그 유형):
  1. **라이브·백테스트 채점 불일치** — 새 로직이 두 경로에서 정확히 같은 규칙을 쓰는가?
  2. **"상한을 넘으면 조용히 버린다"** — 새로운 cap/limit/slice를 도입했다면, 초과분이 어디로 가는지
     명시적으로 처리했는가(watchlist로 흘려보내는 등), 아니면 그냥 사라지는가?
- 커밋 메시지에 적은 의도와 실제 코드 동작이 일치하는지 재확인한다(과거에 어긋난 사례가 있었음).

## 4. 보고
- 발견한 버그는 요약(파일:라인) + 왜 문제인지 + 재현 시나리오로 정리
- 실제로 고친 것과, 확인만 하고 문제없다고 판단한 것을 구분해서 보고
- 버그 아님으로 판정한 항목("기존 설계라 그대로 둠")도 근거와 함께 짧게 언급 — 매번 같은 걸 재검토하지
  않도록

## 5. 커밋/푸시
- 사용자가 명시적으로 요청할 때만 커밋한다. 커밋 전 위 2번 검증이 전부 통과했는지 재확인.
- 다른 세션의 미커밋 파일은 `git add`에 포함하지 않는다 — `git status`로 내가 변경한 파일만 골라 add.
- 푸시 전 `git fetch` + 필요 시 rebase. 다른 세션 작업분이 있으면 1번의 stash 절차를 따른다.
